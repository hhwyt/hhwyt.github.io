# 写文章前的定题面谈

## 一、为什么要有这一步

改「目标：40 岁赚一个亿」那次，返工最多的地方几乎都是结构性问题：论点和例子对不上、标题没坐实、说理顺序不对。这些问题在只有一句话论点、一份大纲的阶段就能查出来，等写成整段散文才发现，返工成本高出一个数量级（改一句大纲是几秒钟，推翻一节已经写完的正文，连带图表、承接下一节的句子全部要跟着改）。这个 skill 就是把这类检查提前到动笔之前。

## 二、跟 deep-interview 的区别

`deep-interview` 是通用需求澄清工具，一轮一问，最多问到 20 轮，目标是把模糊需求钻到接近零歧义，适合工程需求，不适合日更文章：每天一篇的效率要求这一步必须快。所以这个 skill 刻意反着来：

- 一次性批量问完，不超过 6 个问题，每个问题给一个推荐默认值，作者可以整体认可默认值，也可以挑着改，不需要逐条回答。
- 不做多轮 Socratic 追问。问完这一轮就定稿动笔，除非答案里出现新的、明显需要澄清的分歧。
- 如果作者在提出写作需求的时候已经把论点、证据、大纲说清楚了，不需要把六个问题都机械问一遍，直接跳到整理大纲那一步，这个 skill 的目的是拦返工，不是走流程给自己找事做。

## 三、批量问这几条（核心）

1. **核心判断**：这篇文章想让读者读完相信的那句话，一句话写出来，是判断，不是话题。默认：如果作者已经在聊天里说过类似的话，先替他总结一句，让他确认或改，不要空手问。
2. **支撑这个判断的核心证据/例子是什么，这个证据的「严重程度」跟判断精确匹配吗（不夸大也不缩水）**？默认：如果作者提过一段具体经历或数字，先替他核对一遍匹配度，标出可能对不上的地方，让他确认。
3. **文章准备分几节，每节标题现在能不能用一句话说清楚这节要证明或列出什么**？想不出来就标「待定」，不要硬造一个听着高级的词凑数。默认：按论点反推一份 3 到 5 节的大纲草稿，给作者确认或改。
4. **这篇是随笔判断类还是技术讲解类，受众预设是同行还是普通读者**（决定语域，对应 write-skill-v2 的「角色与读者」分支）。默认：随笔判断类，普通读者，除非作者在聊技术方法论。
5. **有没有一篇已发布的旧文章风格上最接近这一篇，可以当参照**。默认：没有强参照就不追问，按 write-skill-v2 的默认风格走。
6. **只发博客，还是也要整理发公众号**（决定要不要提前把配图做成 PNG，避免发布时才发现 SVG 里 pattern/clipPath 在公众号渲染器里会出问题）。默认：只发博客，除非作者说明。

## 四、拿到答案之后

- 把 1-3 的答案整理成一份树形大纲（标题是坐实的结论或者列出的具体内容，不是话题词），发给作者确认。这一步只确认大纲，不写正文。
- 大纲确认后再按 write-skill-v2 写正文，逐节写、逐节自查，不要等全文写完才通读检查一遍，参考 write-skill-v2「参考资料」里的改稿流程。
- 写正文前，自己先按 write-skill-v2 的九条风格要点和禁止清单过一遍再给作者看，机械性问题（破折号、改名漏传播、标题不坐实）不该消耗作者的回合数。

## 五、参考资料

- 这个 skill 解决「写什么、怎么组织」，write-skill-v2 解决「怎么写得像本人」，两个 skill 配合使用，不要合并成一个文件，关注点不一样，合并了以后改起来会互相干扰。
- 这一版针对个人随笔/判断输出类文章，技术讲解类文章的面谈问题不一样（更接近方法论拆解：讲哪几个概念、每个概念配什么例子、要不要正反例对照），需要时单独设计，不在这份 skill 里。
